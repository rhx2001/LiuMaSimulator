# FlowMahjong｜PC 流麻原型开发与学习计划

**版本：** v0.1 · 讨论稿　　**日期：** 2026-11-11  
**用途：** 与本地 Agent 协作开发、自己学习 Niagara，并留下少量能在未来真正复用的实验记录。

> **一句话目标：** 在 PC 上做出一块可以改变重力方向的透明流麻容器：两种颗粒会缓慢移动，不同“油”参数会显著改变运动，亮片能响应光照。先实现可观察、可解释、可复现的效果，再谈真实流体与移动端。

## 01｜项目定位与当前决策

这是一个**可独立验证的图形学实验项目**，不是立刻做成完整游戏或系统动态壁纸。优先建立“做一个小效果 → 比较参数 → 验证 → 留下可复现记录”的循环。

**现在做：** PC / UE5；Niagara 入门；矩形薄层容器；小闪粉、较大亮片；重力方向切换；油的等效阻尼；简易高光；少量可调参数。

**现在不做：** 移动端、陀螺仪、前置摄像头、AR 光照、系统壁纸、多人、存档、复杂 UI、完整 SPH / FLIP 流体、粒子间真实接触堆积、移动端优化。

**技术原则：**

1. **先效果，后抽象。** 首轮使用 Blueprint + Niagara + Material；没有明确复用需求，不提前写插件框架。
2. **区分物理与视觉。** “油让颗粒运动变慢”是模拟；“油看起来透明、染色、折射”是渲染，二者单独验证。
3. **先一块薄平面。** 在 XY（或自选一致的平面）约束颗粒运动，Z 只用于少量层次渲染；后续再提高真实感。
4. **真实物理不是 MVP 验收标准。** 视觉可信、参数响应一致、能解释近似模型，比硬上大型流体求解器更重要。
5. **留可替换边界，而不是过度模块化。** 粒子、油、渲染和控制通过少量参数连接；将来可以独立替换其中某项。

## 02｜第一版效果与验收标准

启动 `L_Prototype` 后，应看到接近正面视角的矩形流麻盒（不必追求写实麻将外形）：

- **两种颗粒：** 小亮粉（Sprite）与较大亮片（Sprite 或简易 Mesh）。初始数量建议约 100–300，仅作为探索配置，不作为性能目标。
- **重力控制：** 用方向键 / WASD 改变容器平面内的重力方向；可重置粒子；暂停时位置保持稳定。
- **三档“油”：** 稀 / 中 / 稠，至少使颗粒沉降和惯性表现出肉眼可辨的差别。
- **边界约束：** 颗粒不能持续穿出矩形；先完成单颗粒对容器边界的约束即可。
- **基础光照：** 旋转一盏虚拟灯，较大亮片高光随法线或朝向变化；透明容器不过度遮挡内容。
- **可观察：** 输出当前重力、阻尼档位、粒子数量，并能录制 15–30 秒对比片段。

**MVP 完成条件：** 不需要颗粒互相碰撞，不需要真实液面起伏，也不要求完全像商业流麻。只要以上行为可复现，就可以进入下一阶段。

## 03｜建议的最小技术结构

```text
L_Prototype
  └─ BP_FlowContainer        # 容器、相机观察区域、按键与参数入口
      ├─ NS_FlowParticles    # 两种粒子行为（多个 Emitter）
      ├─ SM_Container        # 先用简单平面 / 框体几何
      ├─ MI_Oil              # 视觉油层；不负责流体求解
      └─ Light               # 可调整方向、颜色、强度

User.Gravity2D      ──> Niagara：粒子加速度
User.Drag           ──> Niagara：粒子阻尼
User.Bounds         ──> Niagara：边界范围
OilPreset           ──> 同时更新模拟参数与 MI_Oil 参数
```

初期资产建议：`Maps/L_Prototype`、`Blueprints/BP_FlowContainer`、`Niagara/NS_FlowParticles`、`Materials/M_Glitter`、`Materials/M_Flake`、`Materials/M_Oil`、`Docs/EXPERIMENTS.md`。不必为每一个“未来可能出现的类型”提前建立类层次。

**Niagara 的角色：** 一个 System 管理多个 Emitter；Particle Spawn 初始化粒子，Particle Update 持续更新，Renderer 决定怎样呈现。需要复用的行为再从局部 Scratch Pad 整理成独立 Module Script。具体节点名称应按安装的 UE 版本核对，而不是让 Agent 猜测。

**必须警惕：** Niagara 的常规 Collision 模块主要是粒子与场景几何的碰撞，不代表自动完成任意两个粒子之间的接触求解；“大量亮片堆在底部互不穿透”属于单独的后续课题。

## 04｜先用等效模型做“油”

把油分为两组独立属性：

| 模拟属性 | 初期用途 | 备注 |
|---|---|---|
| `Drag`（等效阻尼） | 让颗粒运动衰减更快或更慢 | **不等于**直接模拟真实动力黏度 |
| `GravityScale`（等效沉降） | 区分不同颗粒下沉快慢 | 可用来近似浮力 / 密度差 |
| `AngularDrag` | 控制较大亮片旋转逐步停止 | 与位置阻尼分开 |
| `NoiseStrength` | 少量局部漂浮 / 扰动 | 初期默认为 0，避免掩盖重力模型 |
| 颜色、透光、粗糙度 | 表现油层视觉性质 | 属于材质，不影响粒子位置 |

一个可理解的**近似积分**（并非完整流体方程）是：

```text
v_next = (v + g2D * GravityScale * dt) * exp(-Drag * dt)
p_next = p + v_next * dt
p_next = ClampOrReflectWithinBounds(p_next)
```

`g2D` 是投影在容器平面上的重力方向；统一坐标系与单位。先限制最大 `dt` 或采用稳定的更新策略，避免不同帧率下观感严重分叉。以后真正有需要时，可替换为网格速度场、粒子-流体耦合或专门求解器，而不重写高光材质。

**重要对照：** 固定颗粒类型，只修改油参数；然后固定油参数，只修改颗粒类型。这样才分得清效果到底由什么因素造成。

## 05｜按顺序实施的四个实验

### 实验 A｜粒子能否在薄层中稳定运动？（首个任务）

**做法：** 新建空白 Niagara System；先只做小圆点 Sprite；生成固定数量，尽量长时间存活；限制到一个平面；用外部 `User.Gravity2D` 控制方向；实现矩形边界；提供 Reset。

**验收：** 连续切换上下左右四个重力方向，粒子均能改变运动且不持续越界；暂停后不会继续漂移；低粒子数量也能测试。

**学习重点：** System / Emitter / Module、Particle Spawn vs Particle Update、User Parameters、属性空间、更新顺序。

### 实验 B｜油是否真的让运动发生可区分的变化？

**做法：** 只改 `Drag` 和 `GravityScale`；创建稀 / 中 / 稠三档，暂时不做复杂油材质。选同一初始分布，在三个参数组下分别录屏。

**验收：** 三种油的运动差异清楚可见；参数更改的结果可以解释，而不只是“看上去像”。

**学习重点：** 阻尼、帧率敏感性、参数化、控制变量实验。

### 实验 C｜让两种颗粒呈现不同的材质和运动

**做法：** 保留小闪粉 Sprite，另加较大的六角片 / 星片。开始可用 Sprite，只有需要空间朝向和更明显的镜面反射时再切 Mesh Renderer。给大小、颜色、角速度、沉降参数不同的分布。

**验收：** 两种粒子在外形、运动节奏和光照响应上易于区分；数量变化不会造成明显卡顿或不可解释的消失。

**学习重点：** Sprite 与 Mesh Renderer、材质参数、粒子朝向、透明排序的限制。

### 实验 D｜先做能解释的“假油”，再提高光学质量

**做法：** 一层低复杂度的半透明 / 半透外观材质，先研究颜色、透光、粗糙度与高光；避免一开始叠很多透明层或使用高开销折射。用灯光变化验证闪片反射。

**验收：** 关掉油材质后，粒子模拟不变；切换油颜色后，颗粒轨迹不变；移动灯光时能看到合理的亮片光泽变化。

**学习重点：** 模拟与渲染的解耦、材质混合模式、法线 / 高光、Overdraw。

## 06｜每做完一步都应该做的反例测试

| 现象 | 首先排查 | 不要立即假设 |
|---|---|---|
| 粒子不动 | Update 是否执行、重力变量是否传入、模拟坐标系 | “Niagara 不支持” |
| 重力方向颠倒 | Local / World Space、相机坐标、轴向定义 | “物理公式写错了” |
| 粒子穿边框 | 边界是在积分前还是之后约束、半径是否计入 | “必须用完整碰撞物理” |
| 调阻尼没区别 | 参数是否真正绑定、时间步长、重力与阻尼量级 | “油模型完全无效” |
| 亮片没有反光 | Sprite 朝向、法线、材质与灯光模型 | “必须上复杂折射” |
| 大量粒子时掉帧 | 粒子数、透明重叠、材质复杂度、Niagara Debugger | “一定是模拟太慢” |

每次调参只改一个主要因素；保存旧值；记录**预测→结果是否一致→解释**。不要在没有对照实验前就让 Agent 大规模改动系统。

**建议的 Git 节奏：** 一个实验完成且通过验收后提交一次；提交信息表达行为变化（如 `feat: control particle gravity in 2D`），失败尝试记录在实验日志而不是写成长篇日记。

## 08｜Niagara 笔记：不写百科，只写“可复现证据”

### 为什么以前的笔记可能没发挥作用？

**不是因为你没认真记。** 结合你的描述，更可能有几种机制同时发生：

1. **记录与使用分离。** 笔记散落在语雀、Obsidian 等地方；真正动手时不会自然遇到对应知识。
2. **重读带来熟悉感，而不是提取能力。** “看得懂当时的代码和解释”与“今天能够从空白重新做出来”是两种不同能力。
3. **习惯继续做新题，缺少对照。** 做完后不检查原来哪里判断错了、何时该使用这个方法，就难以把经验转移到下一次。
4. **记录成本太高。** 为了笔记完整而写很久，反而挤占实验、睡眠或复盘时间，笔记于是变成负担。

这些是对**学习流程**的判断，不是对你能力的评价。考试失利的原因也不可能仅凭现在的描述就下定论；但“缺少回顾错误和总结迁移条件”是很值得现在改变的部分。

### 只保留一个入口

不要再专门建立新的 Niagara 知识库。把唯一的工作笔记放在项目里：`Docs/EXPERIMENTS.md`。从 Git 记录、UE 资产路径和短视频中回到证据。等多个项目都出现相同规律时，再提炼成跨项目笔记。

每个实验最多写以下六项，**超过 5 分钟就停止润色**：

```markdown
## [日期] 问题：按键改变重力方向后，粒子为什么没动？
- 目标/预测：按左键，粒子应该整体向左加速。
- 实际结果：粒子不动；调大重力也没用。
- 根因与证据：User 参数没传进 Update；绑定后出现预期变化。
- 复现入口：L_Prototype / NS_FlowParticles；Git commit: abc123。
- 下次闭卷题：Spawn 与 Update 何时执行？怎么验证参数已传入？
```

这不是“学习过哪些 Niagara 知识”的流水账，而是未来重新遇到问题时的**检索路径**。

### 轻量复盘，而不是重新抄一遍

- **每次开始工作前 2 分钟：** 不翻笔记，先说出上一次的目标、修改了什么、一个失败点；再打开工程核对。
- **每完成一个实验：** 先闭卷描述原理与复现步骤，再请 Agent 提问；不会的内容写成下次的一个问题，而不是长篇总结。
- **隔几天重新用到时：** 尝试不看答案重做其中一个关键操作；失败后才查 `EXPERIMENTS.md`。
- **每周最多 10–15 分钟：** 只挑最容易反复犯的 1–2 个错误回顾。忙的时候可以跳过，不要给学习系统再增加“负债”。

**评价标准改成：** 下次能否更快定位、复现与解释？而不是笔记条数、知识树是否完整、今天写了多少页。

## 09｜第一场与 Agent 的对话应该做什么

只讨论**实验 A**，不同时学习所有 Niagara 知识。先准备空白 UE 工程并确认版本，然后：

1. 让 Agent 指导你做出一个固定数量的点粒子系统。
2. 在编辑器里亲手找到 Spawn、Update、Renderer，并解释它们各自负责什么。
3. 接入可修改的二维重力，跑通上下左右运动。
4. 加入矩形边界；若实现卡住，先让 Agent帮你分离出最小复现，而不是改写整个系统。
5. 关掉指导，试着向 Agent 解释数据从按键到粒子位置更新的路径。
6. 将失败点写入 `Docs/EXPERIMENTS.md`，完成首个提交。

**第一个闭卷问题：** 为什么把位置偏移放在 Particle Spawn 与放在 Particle Update 会产生截然不同的效果？

**第二个闭卷问题：** 如果按左键粒子却向右走，你会设计哪两个最小测试来区分“坐标系错误”与“参数没传入”？
